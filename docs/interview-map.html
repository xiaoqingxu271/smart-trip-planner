End-to-End Flow

一次规划的完整旅程（8 步）

从用户点击"生成行程"到拿到可编辑、可导出的完整计划，全程约 30–90 秒。 每一步都标注了背后的工程决策。

提交规划 异步解耦

POST /api/trip/plan/async 立即返回 job_id。限流（429）、并发闸门、相同请求规划锁（409）都在提交时同步判定——冲突立刻反馈，不让用户白等。

后台调度 状态外置

任务进入 pipeline 线程池执行，进度实时写 Redis（job 状态机 pending → running → succeeded / failed，TTL 24h）。客户端断开、关页面、换设备都不丢任务；Redis 不可用时自动降级为同步模式。

结果缓存检查 幂等复用

对请求做指纹哈希（start_date 为空时按"今天"归一化，避免今天和明天命中同一份过期天气的缓存），命中 24h 结果缓存则零成本直接复用。

多智能体流水线 四 Agent 协作

① 景点搜索 → ② 天气查询 → ③ 酒店推荐 → ④ 前三步结果拼接上下文交给 Planner 整合。每个阶段通过回调把真实进度写进 job 状态，前端展示的不是假进度条。

解析与校验 防幻觉核心

剥离 ```json 围栏 → Pydantic 严格校验（失败带错误信息让模型重试一次）→ 确定性校验器检查真实性 / 闭馆日 / 动线距离 / 单日密度；强问题自动带真实替代候选定向修复一次，遗留问题写入 warnings 展示。

图片增强 数据增强而非工具

三层策略：高德 POI 实景照片 → Unsplash 氛围图 → 前端渐变占位。所有外部请求过进程级节拍器统一限速，配 7 天缓存省配额。

入库与缓存 优雅降级

规划结果落 MySQL（自动入库，失败不影响本次返回）→ 完整结果（含图与 trip_id）写 Redis 结果缓存。

轮询渲染与后续交互 产品闭环

前端轮询 GET /api/trip/jobs/{id} 渲染时间线 / 地图 / 预算。后续闭环：手动编辑、收藏、反馈重规划（"约满了/没房了"→局部重规划+版本链）、Plan B 一键对调、导出 PDF / 长图 / iCal、每日真实驾车路线（折线+里程+打车费）。

深拆 1 Agent 底层到底跑了什么：五层调用栈

面试时一句话先说结论："Agent 能力基于官方 openai Python SDK v1 的 Chat Completions 接口与原生 Function Calling 协议； Agent 的'思考-调工具'循环和多智能体编排都是手写的普通 Python 代码，没有用 LangChain / LangGraph，也没有用官方 MCP SDK。" 然后按下表自底向上展开。

L1 传输层HTTPS
向 {LLM_BASE_URL}/chat/completions 发 POST（本项目指向 https://api.deepseek.com，DeepSeek 完全兼容 OpenAI 协议）
L2 模型客户端第三方库
官方 openai Python SDK v1.x：OpenAI(api_key, base_url).chat.completions.create(model, messages, tools, ...)；由框架间接依赖安装（openai>=1.0,<2）
L3 工具协议Function Calling
OpenAI 原生 Function Calling：tools=[{type:function, function:{name, description, parameters(JSON Schema)}}]；模型回 message.tool_calls；程序执行后以 role="tool" 消息回填结果
L4 Agent 执行循环手写 while
SimpleAgent.run()：拼消息 → 带 tools 调模型 → 有 tool_calls 就执行并回填、继续循环；无 tool_calls 就返回文本。最多 3 轮工具迭代（max_tool_iterations=3），本质是一个受控的 ReAct 循环
L5 多 Agent 编排顺序流水线
TripPlannerAgent.plan()：硬编码固定顺序——景点 Agent → 天气 Agent → 酒店 Agent → Planner Agent；Agent 之间不直接通信，中间结果是文本，由程序拼进下一个 prompt
旁路：MCP 通道手写 stdio 客户端
subprocess 启动 npx -y @amap/amap-maps-mcp-server，经 stdin/stdout 收发 JSON-RPC 2.0（initialize → tools/list → tools/call），MCP 工具的 inputSchema 被转成 L3 的 Function Calling schema
面试加分点：能区分"框架名"和"底层协议"两层——hello-agents 只是薄薄一层 Agent 抽象，真正决定能力边界的是 OpenAI Chat Completions + Function Calling 协议，所以换任何兼容模型（DeepSeek/通义/Kimi）业务代码零改动。

深拆 2 一次工具调用的完整消息流（Function Calling 全流程）

以 AttractionSearchAgent 搜索景点为例，这是 L4 循环内部真实发生的消息往返，也是"Agent 为什么能自己调工具"的答案。

system · 程序预置 
你是景点搜索专家，可使用以下工具：maps_text_search / maps_search_detail / maps_around_search。
请把结果整理成带坐标的候选清单……

关键理解：模型本身不会、也无法直接执行任何函数——它只能输出"我想调用某工具"的结构化请求；真正的工具执行、结果回填、轮次控制全是 SDK 外层的 Python 代码完成的。所谓 Agent = LLM + 在一个循环里反复执行它请求的工具。

深拆 3 四个 Agent 如何协作：固定顺序流水线，而非自主对话

很多教程里的多 Agent 是"几个 Agent 在群里自由聊天、互相分派任务"。本项目刻意没有那样做。

# TripPlannerAgent.plan() 的真实形态（简化）
attractions_text = attraction_agent.run(search_prompt(request))   # ① 顺序执行，阻塞等待
weather_text      = weather_agent.run(weather_prompt(request))      # ② 用①的同一 request
hotel_text        = hotel_agent.run(hotel_prompt(request))        # ③
planner_input     = 拼接(request, attractions_text, weather_text, hotel_text)  # 人工拼上下文
trip_json         = planner_agent.run(planner_input)               # ④ 零工具整合
要点本项目的做法
控制流由程序代码 硬编码固定顺序，每一步何时执行、执行几次完全确定
通信方式Agent 之间不直接对话；上游输出是文本，由程序拼接进下游 prompt（相当于"人工传话"）
Planner 的输入人为拼接的干净 Markdown（用户需求 + 三份候选），不含搜索过程的原始噪声
为什么这样设计自主协商型多 Agent 不可控（可能死循环、互相甩锅、token 消耗不可预测）；固定流水线每一步可预测、可测试、可单独重试，更符合工程交付要求

深拆 4 MCP 客户端是手写的：stdio + JSON-RPC 2.0

没有使用官方 mcp Python SDK，而是按 MCP 规范用标准库实现了一个最小客户端（约 180 行）。

# 三次握手式调用，全部走子进程的标准输入/输出
initialize(protocolVersion="2024-11-05", clientInfo=...)  # 协商能力
tools = tools/list()                              # 拿到 12 个工具的 name/description/inputSchema
result = tools/call(name="maps_text_search", arguments={...})

# 关键桥接：MCP inputSchema  →  Function Calling 的 parameters
# 于是模型能"看见"高德工具并按正确参数发起调用
工程细节说明
消息格式每行一个 JSON-RPC 2.0 帧：{"jsonrpc":"2.0","id":N,"method":...}，后台线程持续读 stdout，按 id 把响应放入 _pending 表
线程安全（双锁）_io_lock 把"写请求→等响应"整个周期串行化（否则并发线程会互相清掉响应）；_lock 只保护 id 计数与响应表
单例子进程全进程只启动一个 npx MCP 子进程，三个 Agent 共享；模块导入时即创建初始化锁，防止并发首调建出两个子进程
确定性代码旁路校验器/地理编码不经模型 function calling，直接拿 client 句柄显式调指定工具，省一次模型决策

深拆 5 和 LangChain / LangGraph / CrewAI 的区别（面试高频追问）

面试官问"为什么不用 LangChain/LangGraph"时，不要说"没学过"，要按抽象层次和场景回答。

方案编排模型工具/循环状态与持久化适合场景
本项目
轻量抽象 + 手写循环		 固定顺序流水线，硬编码在普通函数里 原生 Function Calling，手写 while（≤3 轮） 会话/结果存 MySQL+Redis，无框架状态机 流程固定、追求可控、想吃透底层原理
LangChain Chain / LCEL 表达式组合，线性为主 大量 Tool 封装与 Agent 实现，集成生态最全 靠各模块自行组合，抽象层多、版本变动快 快速拼装、需要大量现成集成与文档
LangGraph 显式有向图 StateGraph，原生支持循环/条件分支 图节点内调工具，ToolNode 标准化 Checkpointer 检查点、时间旅行、断点续跑、人机协同中断 复杂循环、多分支、需要中断恢复的生产级 Agent
CrewAI / AutoGen 多 Agent 自主对话、角色分工协商 Agent 自主决定是否调用，控制流涌现 对话历史驱动，确定性较弱、token 成本高 开放式任务、探索性协作、难以预先固定流程
标准回答话术："我的业务流程是固定的四段式，用 LangGraph 建图属于过度设计；用 CrewAI 的自主协商又会牺牲确定性。我选择在原生 Function Calling 上写最小循环，把编排逻辑留在自己可读可控的代码里。但我清楚边界：一旦出现条件分支、循环重试或需要人工审批断点，我会迁移到 LangGraph 的 StateGraph + Checkpointer——它解决的正是我现在硬编码的那部分问题。"

A可靠性架构

长耗时 AI 任务的工程化承载：任务解耦、并发治理、故障降级。

1 · 长任务异步化：Job 提交 + 轮询 + 自动降级

LLM 流水线 30–90s，不能挂在 HTTP 请求生命周期里。HTTP 只受理与查询，执行进后台线程池，状态机（pending/running/succeeded/failed）写 Redis 存 24h。关页面、刷新、换设备都能取回结果；Redis 不可用自动退回同步模式，旧体验无损。

话术："AI 生成类产品第一课就是把任务从请求生命周期里解耦出来——HTTP 负责受理，状态外置，客户端断开不影响执行。"

2 · 并发控制三件套：闸门 / 锁 / 缓存

Semaphore(2) 闸门：只有 2 个流水线 worker，第 3 个请求快速失败 429 而不是排队到 axios 120s 超时；规划锁：Redis SETNX + 所有权 Token + Lua 原子比对释放——防止 A 的锁超时过期被 B 拿走后，A 的 finally 误删 B 的锁；结果缓存：请求指纹 24h 复用，空日期归一化保证缓存正确性。

话术："闸门管总量、锁管去重、缓存管复用，三种手段各管一件事，不混用。"

3 · 全链路降级与 10 秒熔断静默期

MySQL / Redis 双库独立探测、独立降级：Redis 挂 → 缓存退进程内存；MySQL 挂 → 规划照常、历史功能提示暂不可用。关键设计：探测失败后进入 10s 静默期快速失败——否则 Redis 宕机时每个请求都要等 1.5s 探测超时，4 个 IO worker 会被限流中间件的每请求检查全部占满，一次缓存故障被放大成全站卡死。

话术："降级不是到处 try/except，是识别并切断故障放大路径——这是我专门修过的一个全站卡死问题。"

BAI 工程化

LLM 不可信怎么办：用确定性代码兜住生成质量，用流程设计补数据缺口。

4 · 混合校验防幻觉：确定性规则，0 LLM 成本

Planner 输出后跑确定性校验器：真实性——POI 在高德核实到但坐标偏差 >1.5km（haversine 纯计算）判疑似编造；闭馆日——逐景点查真实营业时间，按每一天自己的日期判断星期冲突；动线——同日相邻景点驾车 >15km；密度——单日 >3 个。全部不耗 LLM，配 7 天缓存。

话术："防幻觉不靠提示词求模型，靠生成后的确定性核验——能用代码判断的绝不问模型。"

5 · 带约束的定向修复：候选坐标原样注入

发现强问题后，先用 maps_around_search 搜出真实周边替代候选（名称/地址/坐标来自真实 POI），注入修复提示词并要求"坐标原样使用、禁止编造"，Planner 只做一次定向修复；仍不达标则进 warnings 透明展示。直线距离预筛省配额：驾车距离 ≥ 直线距离，直线 >15km 必超标、<8km 必达标，只对中间地带调 API。

话术："让模型改错时给它真实素材，而不是让它凭记忆重编——修复的输入决定了幻觉的下限。"

6 · 局部重规划：只重写受影响的天

用户反馈"约满了/没房了"→ 自动检测影响的日期（酒店反馈影响全部天）→ LLM 只重写这些天 → 后端确定性合并回原计划，未受影响的天逐字保留——更快、更稳、不误伤满意安排。新版本 parent_id 挂版本链可回看。实时房态个人 Key 拿不到，用"用户反馈 → 约束重规划"的流程方案补位。

话术："数据不可得时，用流程设计补产品能力——这是一个工程判断，不是技术炫技。"

C协议与外部依赖治理

框架没有的东西自己造，三方限制主动治理。

7 · 手写 MCP stdio 客户端，桥接到 Function Calling

所用框架未内置 MCPTool，按 MCP 规范自实现：子进程启动官方高德 MCP 服务器，stdin/stdout 收发 JSON-RPC 2.0（initialize → tools/list → tools/call），auto_expand 把 MCP 工具自动展开为框架原生 Tool 走 function calling，参数 schema 直接取自 MCP inputSchema。多线程共享单连接时，写请求与等响应在同一临界区，防止响应被并发请求清掉。

话术："读协议规范、手写协议客户端，并想清楚多线程共享连接时的消息交错问题。"

8 · 最小权限：工具白名单的两处强制

每个工具型 Agent 只暴露白名单内的 MCP 工具（景点 3 个、天气 1 个、酒店 1 个）。白名单在展开时过滤与父工具 run 入口拦截两处强制——因为框架在展开失败时会退回注册父工具，父工具可透传任意 MCP 工具名。白名单含服务器不存在的工具名时显式告警，防拼写错误静默失效。

话术："Agent 的行为面要收窄：模型不该有的能力，就不该出现在它的工具列表里。"

9 · 全局节拍器 + 三层图片管线 + 安全代理

节拍器：Agent 经 MCP 的调用、校验器、图片服务共享同一高德 Key 的 QPS，进程级 pace() 在锁内睡眠、全局串行，相邻调用起始间隔 ≥0.35s，比"调用后固定 sleep"省 N 次尾部等待。图片：高德实景 → Unsplash → 占位图三级降级；同源代理解决防盗链/混合内容/导出跨域污染——域名白名单、逐跳重定向复查（防白名单域 302 到内网）、魔数嗅探真实类型、未知图床直接 400 不做开放重定向。

话术："共享配额的调用方要共享同一个节拍器；做一个图片代理顺手就要堵住开放重定向。"

D安全与质量保障

鉴权、限流的细节设计，以及一套不打真实 API 的测试体系。

10 · 三形态鉴权与多用户隔离

AUTH_MODE 三态互斥：none（本地演示）/ 访问码 / 多用户（注册登录 PBKDF2 + Redis 会话 7 天）。行程按用户隔离：示例作品与无主历史全员可读、仅本人可改删；异步 Job 绑定 user_id，仅本人可查。开启鉴权时同时关闭公开 API 文档。

话术："鉴权不是加个中间件就完了——每个新端点（包括轮询）都要回答'谁能看'。"

11 · 限流与中间件顺序的细节

固定窗口计数用 Lua 脚本原子 INCR + 首次 EXPIRE，fail-open（Redis 挂不限流保可用）；401 也计入限流配额，天然抑制暴力枚举；注册/登录独立 10 次/分/IP。中间件注册顺序 = 后注册者在外层：鉴权最内、限流中、CORS 最外——保证 429/401 响应也带跨域头，浏览器才能读到错误信息。

话术："429 响应没跨域头，前端拿到的是 opaque error——这类问题逼你理解中间件洋葱模型的真实执行顺序。"

12 · 43 个测试用例 + 服务容器 CI

覆盖：请求边界、校验器规则（FakeClient 不打真实 API）、MCP 白名单两处强制、三形态鉴权、限流（栈构建后注入确定性 FakeCache，结果可复现）、规划锁与存储语义；需真实 Redis 的用例不可用时自动 skip。CI 双并行任务：后端拉起 MySQL 8.4 + Redis 7 服务容器（健康检查通过才跑）全量无 skip；前端 vue-tsc 类型检查 + 构建 + vitest。

话术："测试不依赖真实三方 API，但 CI 里用真实 MySQL/Redis 把降级路径也测满——skip 归零。"
War Stories

踩坑实录：现象 → 根因 → 解法

面试最爱问"遇到过什么难的问题"。以下每条都有完整的排查故事可讲。

1 · redis-py 8 连不上本地 Redis 5

现象
连接报 unknown command 'HELLO'。
根因
redis-py 8 默认 RESP3 握手发 HELLO，Redis <6.0 不支持。
解法
客户端强制 protocol=2（RESP2），并在 README 记录环境约束。

2 · 高德并发调用触发限流

现象
批量查 POI 时报 CUQPS_HAS_EXCEEDED_THE_LIMIT。
根因
个人 Key 约 3 QPS，Agent / 校验器 / 图片服务各自调用会叠加超限。
解法
进程级全局节拍器：锁内睡眠保证相邻调用起始间隔 ≥0.35s，所有调用方共用一把计拍。

3 · MCP 共享连接的响应丢失

现象
多 Agent 并发时偶发请求等待超时。
根因
两个线程交错发起请求时，先到者的响应可能被后到者的 _pending.clear() 清掉。
解法
「写请求 → 收响应」整个周期持请求级互斥锁；另一把锁只保护 id 计数与响应表。

4 · 惰性单例建出两个 MCP 子进程

现象
并发首调时偶现子进程泄漏。
根因
锁在惰性初始化时才创建——两个线程可能各拿一把新锁同时通过判断。
解法
锁提升为模块导入时创建 + 双重检查；代码里写明注释防回归。

5 · Redis 宕机放大成全站卡死

现象
Redis 掉线后整站所有请求变慢直至不可用。
根因
限流中间件每请求探测，1.5s 超时 × 每请求，4 个 IO worker 被占满。
解法
探测失败进入 10s 熔断静默期：期间直接快速失败并走降级，不碰 socket。

6 · 空日期请求命中过期缓存

现象
不带出发日期的请求，第二天返回的还是昨天的天气。
根因
start_date 为空时序列化指纹不含日期，今天和明天哈希相同。
解法
计算指纹前把空 start_date 归一化为"今天"再哈希。

7 · 高德图床三连坑：防盗链 / 混合内容 / 假类型

现象
图片挂、https 页面拦 http 图、部分 CDN 标 octet-stream。
根因
图床混杂（autonavi/amap/alicdn），各 CDN 行为不一致。
解法
同源代理：白名单域 + 逐跳重定向复查 + 魔数识别真实类型 + 磁盘缓存 + http→https 升级。

8 · 导出 PDF 丢图 / 地图渲染冲突

现象
html2canvas 截图丢图；带地图导出渲染异常。
根因
跨域图片污染 Canvas；地图 Canvas 与 html2canvas 兼容性差。
解法
图片全部走同源代理（useCORS 可生效）；导出时隐藏地图组件，与社区已知结论一致。
Interview Script

电梯陈述与高频追问

建议的讲述节奏：先用 30 秒讲清产品与架构全貌 → 让面试官选感兴趣的方向 → 从下面的亮点/踩坑里挑对应的两三个深挖。主动权在你手里。

30 秒版本

"我独立完成了一个多智能体旅行规划应用，底层基于官方 openai SDK 的 Function Calling，没有用 LangChain/LangGraph： 四个 Agent 里，三个工具型 Agent 经我手写的 MCP stdio 客户端调用高德地图 12 个真实工具搜景点、天气、酒店，一个零工具的 Planner 按固定顺序流水线整合，输出结构化行程。 因为 LLM 输出不可信，我设计了一套确定性校验器做生成后核验——真实性、闭馆日、动线距离、行程密度四类规则零 LLM 成本， 发现问题就带着真实替代候选让模型定向修复。工程侧把长任务异步化、双库存储带全链路降级、全局 QPS 节拍器治理第三方限流， 配了 43 个不打真实 API 的测试用例和真实 MySQL/Redis 服务容器的 CI。整个项目大概 3700 行后端核心代码，从 MCP 协议客户端到 Agent 循环、鉴权限流都是自己写的。"

你的 Agent 底层到底用了什么框架？是 LangChain / LangGraph 吗？
都不是。自底向上：传输是 HTTPS 调 OpenAI 兼容的 /chat/completions（实际接 DeepSeek）；客户端是官方 openai Python SDK v1；工具能力用 SDK 的原生 Function Calling；Agent 的"调工具→拿结果→再思考"循环是 SimpleAgent.run() 里手写的 while 循环（最多 3 轮）；四个 Agent 的协作是 plan() 里硬编码的固定顺序流水线。外层用的 hello-agents 只是《Hello Agents》一书的薄教学抽象，真正的能力边界由 Chat Completions + Function Calling 协议决定。没用 LangChain 是因为流程固定、不需要它的链式抽象与庞大集成；没用 LangGraph 是因为没有条件分支/循环/检查点需求，建图是过度设计——但出现这些需求时我会迁移到 LangGraph。
Function Calling 的完整流程是什么？模型是怎么"调用"函数的？
要先纠正一个常见误解：模型本身不能执行任何函数。流程是：① 程序请求时在 tools 参数里给模型一份工具清单（名称、描述、参数 JSON Schema）；② 模型若判断需要工具，返回的不是普通文本，而是结构化的 tool_calls（函数名 + 参数字符串）；③ 程序（不是模型）在本地执行真正的函数——这里是经 MCP 调高德工具；④ 把执行结果以 role="tool" 的消息追加到消息列表再次请求；⑤ 模型基于结果继续，要么再发 tool_calls 进入下一轮，要么输出无 tool_calls 的最终文本，循环结束。Agent 本质 = LLM 外套一个"反复执行它请求的工具"的循环，循环次数、工具执行、超时控制都是普通代码。
多个 Agent 之间是怎么通信的？
它们不直接通信、也不互相对话。编排器 TripPlannerAgent 按固定顺序调用每个 Agent，拿到的是文本形式的中间结果（景点候选表、天气文本、酒店候选表），再由程序把这些文本和用户需求拼接成 Planner 的输入。这是一种"中心化编排 + 黑板式传参"：上游产出写进同一块上下文，下游只读这块上下文。好处是没有 Agent 间的对话噪声与不可控的 token 消耗，每一步输入输出都可单独测试和重试；代价是流程变更要改编排代码——对本项目固定的四段流程不是问题。
为什么用 MCP，而不是直接调高德 REST API？
三个理由：① 工具自描述——MCP 的 tools/list 直接返回工具名、描述与参数 JSON Schema，auto_expand 后就能走 function calling，接入新 MCP 服务器不需要改 Agent 代码；② 协议标准化——工具生态正在向 MCP 收敛，这是对方向的押注；③ 但我也保留了务实的一面：确定性代码（校验器、地理编码）不走 LLM 的 function calling，直接拿 client 句柄显式调工具，省掉一次模型决策的成本与不确定性。
为什么拆四个 Agent，一个 Agent 全干不行吗？
核心是上下文隔离。搜索型任务工具调用轮次多，中间结果（POI 列表、原始 JSON）噪声很大；如果让一个 Agent 边搜边规划，搜索噪声会污染规划上下文，输出 JSON 的稳定性也差。拆开后：三个搜索 Agent 各自的小上下文里专心调工具，Planner 的输入是人为拼接的干净结构化上下文，且它零工具——行为完全可预测，输出的 JSON 解析失败率显著更低。另外每个 Agent 的工具白名单不同，这也是最小权限的自然实现。
怎么防 LLM 编造景点和坐标？
四道防线：① 提示词约束——要求只输出 JSON、禁止编造；② 结构校验——Pydantic 强类型模型，失败带错误信息重试一次；③ 确定性核验——POI 在高德核实不到仅弱提醒，核实到但坐标偏差 >1.5km 判疑似编造（强问题，haversine 纯计算零配额）；④ 修复注入真实素材——把周边搜索的真实 POI 候选连名称带坐标喂给模型，要求原样使用。LLM 只在"给真实素材做选择与编排"，不负责"从无到有编造事实"。
异步任务为什么用 Redis 存状态，不用 Celery / 消息队列？
取舍于部署形态：这是单机单进程应用（README 里显式声明了这个约束），Celery 会引入 worker 拓扑、broker 运维、序列化与监控一整套成本，收益不成比例。我用 Redis KV 存任务状态机 + 线程池执行，40 行代码解决问题，且 job 语义（提交/查询/状态机/TTL）已经抽象出来——将来量上去了，把执行器换掉、状态换 broker，接口不用动。同时设计了降级：Redis 不可用自动退同步模式。
单进程是有意的吗？流量涨了怎么演进？
是有意取舍并诚实声明的：MySQL 单连接、单个 MCP 子进程、进程内缓存、并发闸门都建立在单进程假设上，多 worker 会破坏正确性，所以 README 明确要求 --workers 1。演进路径我想过：MySQL 换连接池、MCP 客户端池化或换长连接服务、进程内缓存全部收敛到 Redis、节拍器换分布式令牌桶、Job 执行器换独立 worker + broker、图片代理上 CDN 与对象存储。关键是每一步改哪一层我都清楚，因为降级边界是按层画的。
这个项目里你觉得最有价值的一个设计？
混合校验 + 带约束定向修复这一对组合。它回答了 AI 应用最核心的问题："模型输出不可信时，产品怎么保证质量"。我的答案是：把"判断"留给确定性代码（便宜、可靠、可测试），把"生成"留给模型，但生成时的素材必须来自真实数据源。落地效果是幻觉坐标被系统性拦截、修复只花一次 LLM 调用、遗留问题透明展示给用户而不是默默吞掉。这个思路可以平移到任何"生成结构化事实"的 AI 应用。
